### How the oracle works

Each fixture is a self-contained VB6 mini-project plus an `expected.json` that
states the **correct VB6 semantics**, not the current behaviour. The runner
indexes it through the real pipeline (extraction → resolution → SQLite) and
compares. `expect` entries must be found, `forbid` entries must not — the
`forbid` half is what makes the suite useful against false positives, which
the specification ranks above recall.

A fixture whose semantics are not implemented is marked `known-gap` with a
reason; the runner then asserts the gap is *still there* and fails with
"promote to pass" the moment it closes. That is what kept the suite green and
honest while the engine was being built: 29 → 44 → 56 passing across the three
stages, with the gap list shrinking 26 → 11 → 0.

## Regressions

```bash
npm test
```

```
Test Files  164 passed | 15 skipped (179)
     Tests  2958 passed | 178 skipped (3136)
```

No failures. VB6 support adds a language, three extractors, a resolver branch
and a synthesizer without changing behaviour for any existing language. The
three core edits — `candidates` propagation, `ResolvedRef.metadata`, the VB6
branch in `resolveOne` — are additive: no other language reads `candidates`,
the new metadata field is optional, and the branch is entered only for
`language === 'vb6'`.

## Behaviour on a sample project

A four-file project (`.bas` + `.cls` + `.frm` + `.vbp`) exercising forms,
controls, a control array, an OCX, `WithEvents`, `RaiseEvent`, `Implements`,
`With`, qualified calls and COM references:

| | Value |
|---|---|
| VB6 nodes | 44 |
| Edges | 79 |
| Synthesized (event bindings) | 6 |
| Unresolved references | 9 |

All nine unresolved are external by nature: VB6 intrinsic functions (`CStr`,
`MsgBox`), standard control types (`CommandButton`, `Frame`, `Timer`,
`MSComm`), control properties (`Input`, `Interval`) and one interface that the
fixture deliberately does not define.

### Effect of the two fix rounds

Same project, same query, at each stage:

| | after extraction only | after extractor fixes | after the resolver |
|---|---|---|---|
| Unresolved references | 44 | 9 | 9 |
| Qualified call `Module1.DoWork` | → `Module1` (wrong) | → `DoWork` | → `DoWork` |
| `c.Compute v` | → `c` (wrong) | → `Compute` | → `Compute`, via c's type |
| `With` members | nothing | resolved | resolved |
| Event handlers | unlinked | unlinked | bound to their producers |
| `Private` cross-module call | bound (wrong) | bound (wrong) | unresolved (correct) |

## MCP surface

Verified through the CLI, which runs the same handlers as the MCP tools:

- `query` finds VB6 symbols with signature and location;
- `callers` on an event handler returns both its `WithEvents` field and the
  `Event` declaration in the producing class;
- `impact` walks VB6 edges across files;
- `node` returns the **full procedure body** plus the caller/callee trail;
- `explore` leads with a "Dynamic-dispatch links" section rendering each event
  binding as `VB6 WithEvents event \`ItemRead\` @Form1.frm:28` — the label and
  the wiring site — and returns verbatim source in ```vb6 blocks.

## Not covered

No large real-world VB6 project has been indexed yet, so parse robustness at
scale, performance, and the resolution rate on production code are unmeasured.
The agent A/B flow validation the repo expects per language has not been run
for VB6 either, for the same reason. See `OPEN_QUESTIONS.md`.
